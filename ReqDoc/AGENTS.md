# 2. 标准工作流：三段式交付

用户使用高能力模型设计方案；AI 负责把方案转成**页面上可见的步骤**供用户确认，确认后才实施。
**三段之间不得跳步。**

## 2.1 第一段：资源核查（只读，不改文件）

只读与任务直接相关的文件，不扫描整个项目。必须输出**资源清单**：

- 已有参数（`.vparam` 中的分组与具体参数名、默认值）
- 已有 CAPL 可调用节点（`.can` 中 `export testfunction` 的函数名与签名）
- 已有 Test Table Function / Test Case / Test Sequence
- 已有系统变量（以 `.can` 中实际引用的 `@sysvar::<命名空间>::<变量>` 为准）
- 已有固定模板（Preparation / Completion 格式）

资源清单必须来源于实际文件。**清单外资源一律禁止使用。**
缺少必要资源时停止设计并向用户询问，不得自行创建替代资源。

## 2.2 第二段：页面伪代码确认（唯一允许的沟通凭据）

**此段不写任何代码。** 只输出用户能在 vTESTstudio 页面上逐行对照的步骤表。

用户只看“Command + Caption + 调用对象 + 封装”四列判断流程，不需要审代码。
用户未明确确认前，禁止开始实施。

## 2.3 第三段：实施与验证

顺序固定：**先参数 → 再结构 → 最后函数**，每改一类立即编译。

- 每次修改都必须实际编译，并贴出 `lastbuild` 中 `Compilation succeeded/failed` 的原文。
- 无法实际编译时，明确说明“尚未验证”，不得声称编译通过。
- 完成后报告：改了什么、改了哪些文件、验证结果、未解决问题。

## 2.4 页面伪代码格式（强制四列）

| Command | Caption（页面显示的中文） | 调用对象 | 封装 |
|---|---|---|---|
| Test Case | 10 V 休眠平均电流 | `SleepCurrent(OutPutVoltage=10)` | Test Case，内部循环 N 轮 |
| CAPL Function | 关闭电源输出 | `PWR_Off_Check()` | 调 `.can` 的 testfunction |
| Await Value Match | 等待 DVM 到目标 ±0.5 V | `N8361::DVM_Voltage` `range/based` | 原生节点，超时用参数 |
| State Check | 判据：平均电流 < 0.250 mA | `StaticCurrent_Avg` `< SC_AvgLimit_mA` | 原生节点 |
| CAPL Inline | 轮次加一 | `Repeat = Repeat + 1` | 仅赋值 |
| Wait | 保持 LIN 通讯 | `SC_LinRun_ms` | 原生节点 |

**“封装”列不可省略。** 必须写清是 Test Case、Test Table Function、CAPL Function 还是原生节点。

# 3. API 真实性约束（最高优先级）

## 3.1 禁止虚构 API

1. 严禁编造函数、类、变量、结构体、枚举及系统变量。
2. 严禁将其他软件、其他版本或其他编程语言的 API 直接套用到当前项目。
3. 严禁为了实现需求而擅自设计驱动不存在的接口。
4. 不允许将未经验证的 API 当作真实接口使用。
5. 不允许为了让代码看起来完整而自行补充不存在的接口。

## 3.2 API 验证优先级

1. 当前项目已有的实际调用方式。
2. 当前安装版本的 SDK、头文件、接口定义。

5. 其他版本的资料，仅供参考，不得直接认定兼容。
6. 模型自身知识和推测，不得作为接口存在的依据。

涉及 API 时优先核实：函数名称、参数类型及顺序、返回值、结构体定义、调用约定、版本兼容性。

## 3.3 不确定时的处理

- 找不到接口定义时，优先搜索项目文件、SDK 和驱动示例。
- 仍然无法确认时，明确说明缺少什么资料。
- 不允许通过猜测接口、创造替代接口解决问题。

# 5. VTT / vTESTstudio 专项规则

## 5.1 页面步骤输出要求

- 使用 Markdown 表格，直接展示 Test Tree / Test Table 页面步骤。
- 按实际执行顺序排列，明确 Preparation、测试执行、Completion 的位置。
- 每个步骤标注实际调用的 TestCase 或函数，并标明封装形态。
- 不输出未经确认的代码实现。
- 不引入清单之外的变量、函数或测试组件。

## 5.2 TestCase 复用规则

1. 必须优先复用项目已有封装 TestCase。
2. 禁止重复实现已有 TestCase 内部逻辑。
3. 禁止将已有封装逻辑拆开重新实现。
4. 每个测试步骤必须标注实际调用的 TestCase 或函数。
5. 没有合适的封装 TestCase 时，明确指出缺失，不得假装已有。

## 5.3 Preparation / Completion 固定格式

1. 严格使用用户提供的 Preparation 固定格式。
2. 严格使用用户提供的 Completion 固定格式。
3. 不得增删字段、修改字段顺序或字段名称。
4. 不得自行设计新的格式。
5. 未获得原始模板时，必须向用户索取，不得猜测。

## 5.4 节点选择原则

1. **流程必须写在 Test Table 的 Function 和 Test Case 里，步骤要在页面上看得见。**
   禁止用一个 CAPL 函数包住整套流程。
2. 能用原生节点就用原生节点：`awaitvaluematch`、`statecheck`、`wait`、`set`、
   `linstopscheduler`、`linstartscheduler`、`while`。
3. 不手写轮询循环；需要等待条件时优先用 `awaitvaluematch`。
4. CAPL Inline 只做少量补充，且只能使用 `@sysvar::`、`syspar::` 与 CAPL 内建函数。
5. 参数填错类校验一律不加；只保留写坏变量或安全互锁相关的约束。
6. 判据参数（容差、限值）不得放进 Mode 分列，否则等于允许调试时放宽判据。

## 5.5 输出前强制自查

- 所有变量均在资源清单内。
- 所有函数均在资源清单内。
- 所有 TestCase 均为已有资源。
- 已复用已有封装 TestCase。
- 没有重复实现已有逻辑。
- Preparation / Completion 格式完全一致。
- 所有步骤符合实际测试流程。
- 没有虚构任何资源或接口。

**有一项不符合，必须重新检查；资源不足则停止并询问用户。**

# 6. 已验证技术事实（免重复验证）

以下均为本工程实测确认，可直接使用，不必再试。

## 6.1 编码

| 文件 | 编码 | BOM |
|---|---|---|
| `*.vtt` | UTF-8 | **有** |
| `*.vparam` | **GBK(936)** | 无 |
| `*.can` | **GBK(936)**，首行 `/*@!Encoding:936*/` | 无 |
| `*.vvarprop` / `*.vtsoproj` | UTF-8 | 有 |

## 6.2 CAPL 与报告

| 事实 | 影响 |
|---|---|
| CAPL Inline 是独立编译单元 | 不能调用 `.can` 的函数或变量（报 `1156 unknown function` / `1053 Unknown symbol`）。要调用就写 `<caplfunction>` |
| `write()` 不产生报告步骤 | 只有 `testStepPass` / `testStepFail` 会成为报告里的步骤 |
| `testWaitForTimeout` 每次调用都记一条报告 | 轮询间隔用 200 ms，不要用 10 ms |
| CAPL 无 `Sleep` / `Delay` 类函数 | 已查 vTESTstudio CHM 的 418 个 Test 函数，无免记录的纯延时 |

## 6.3 Test Table 语法

| 事实 | 说明 |
|---|---|
| `<export>` 只能是布尔 | 写 `none` 会 schema 校验失败，整份 VTT 打不开 |
| `<caplfunction>` / `<ttfunction>` 不可混用 | 前者调 `.can` 的 `export testfunction`，后者调 Test Table 内部 Function |
| `<caplfunction>` 可用于 Test Case 内 | 已实测编译通过 |
| `statecheck` 支持 `range/based` | 上下界一次表达，不必写两个判断；也支持一个 `expected` 内多个 `compare` |
| `awaitvaluematch` 超时可引参数或变量 | 但不能在 XML 里做加法，需先用 Inline 算好再引用 |

## 6.4 dbobject 路径格式（写错即编译失败）

```
系统变量：SysVar_BEGIN_OF_OBJECT|1|变量名|命名空间|-1|0|END_OF_OBJECT_SysVar|
参数：    ChParScalar_BEGIN_OF_OBJECT|1|IBS::参数名|END_OF_OBJECT_ChParScalar|
网络：    Network_BEGIN_OF_OBJECT|1|LIN|5|1|END_OF_OBJECT_Network|
```

## 6.5 继电器语义（按接线图确认）

| 通道 | 触点类型 | 0 | 1 |
|---|---|---|---|
| `BatteryConnectEquipment` | 常开 | 未连接 | 接入电池 |
| `CAB1500_PowerCtrl` | 常闭 | **接通** | **断开** |
| `IBS_PowerCtrl` | 常闭 | **接通** | **断开** |

- 休眠电流测量要求 CAB1500 接通，即准备态元组应为 `(0,0,0)`。
- 带电切换禁止：`RELAY_Set` 要求输出已关且 DVM 低于 `TB_MaxSwitchVoltage_V`。
- 测试中确需切换继电器时，用 `RELAY_SafeSwitch_Check(state)`：内部先关输出、等电压落下、再切、再恢复。

## 6.6 Mode 参数分列

- 用 `ScalarMultiRecord` + `SelectorType	[Mode]		Normal	Test`。
- 多列记录的 `Type` **必须写 `Auto`**，不能写 `Integer` / `Float`。
- 同一 Group 内可以同时存在 `ScalarSingleRecord` 与 `ScalarMultiRecord` 块。
- `Mode` 的 `PossibleValues` 为空不影响列绑定。
- `Mode` 绑定关系存放在 `.vtsoproj` 的测试单元 `EmbeddedTUVariantProperties` 里，
  同时 `.vvarprop` 中该属性的 `Modifiable` 需为 `true`。

# 7. 文件操作规范（防损坏）

1. 修改任何工程文件前先备份到 `%TEMP%`。
2. 读写必须使用文件本身的编码；禁止用 UTF-8 工具生成中文后按 GBK 写入。
3. **禁止用行号下标做逐行替换**，会因行号偏移错删代码。改用正则整块匹配。
4. 每次写回后立即校验三项：文件长度未异常变化、关键标记仍在、`0xFFFD` 计数为 0。
5. 临时脚本一律放 `%TEMP%`，不落在工程目录。需要长期保留的放 `ReqDoc/tools/`。
6. 大括号配平检查：写入前后统计 `{` 与 `}` 数量必须相等。

# 8. 编译与验证

1. **没有命令行编译。** 只能用编辑器 Home → Build All Test Units（F6）。
2. 构建日志：`obj_IBSProject\<测试单元Guid>.lastbuild`（UTF-8）。
3. 判定成功的关键字：`# Compilation succeeded` 与 `# Test unit created`。
4. 日志只显示 `is up to date` 属**增量构建**，不代表失败；要强制全量需改文件时间戳。
5. F6 无效时先排查环境，不要怀疑代码：编辑器是否前台、是否有“文件已被另一程序修改”对话框。
6. `.vtuexe` 是 ZIP 容器，内含原始源码与 `__TsoBuildFiles_/*.cbf`，可解包核对改动是否真的进了产物。
7. 报告核对：`.vtestreport` 是加密二进制，需先导出 PDF/XML；
   PDF 可用 `ReqDoc/tools/extract_report_text.py` 转纯文本。
