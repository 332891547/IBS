# 2. 标准工作流：三段式交付

用户使用高能力模型设计方案；AI 负责把方案转成**页面上可见的步骤**供用户确认，确认后才实施。
**三段之间不得跳步。**

## 2.1 第一段：资源核查（只读，不改文件）

只读与任务直接相关的文件，不扫描整个项目。必须输出**资源清单**：

- 已有参数（`.vparam` 中的分组与具体参数名、默认值）
- 已有 CAPL 可调用节点（`.can` 中 `export testfunction` 的函数名与签名）
- 已有 Test Table Function / Test Case / Test Sequence
- 已有系统变量（从本任务实际引用的 `.can`、VTT、数据库/配置中核实；记录变量来源，不凭名称或模型知识推断）
- 已有固定模板（Preparation / Completion 格式）

资源清单必须来源于实际文件。**不得把未核实或未获确认的资源当作现有资源使用。**
缺少必要资源时指出缺项和影响；如需新增替代资源，先在页面设计中明确标注“拟新增”并取得用户确认，未经确认不得创建。

## 2.2 第二段：页面伪代码确认（唯一允许的沟通凭据）

**此段不写任何代码。** 页面设计必须按以下两层完整输出，不能只给总序列或只给某个 Test Case 的步骤：

1. **最终 Sequence / Test Tree 结构**：按实际顺序列出 Preparation、每个 Test Case 实例、实例间 Wait、Sequence Completion；重复实例须逐个列出并标注参数/轮次。
2. **每个 Test Case 内部步骤**：每个独立 Test Case 各自给出从第一步到最后一步的完整页面步骤表。不得用“同上”“内部执行既有流程”省略关键步骤；若多个 Case 确实共用同一已确认定义，可明确指出共用定义，并只列一次该定义的完整步骤。

最终 Sequence 结构表与 Case 步骤表均使用四列：`Command`、`Caption（页面显示的中文）`、`调用对象`、`封装`。每一行对应页面上实际可见的节点，执行顺序须明确。

用户未明确确认前，禁止开始实施。用户只需确认页面流程与判据，不要求审阅代码。

## 2.3 第三段：实施与验证

顺序固定：**先参数 → 再结构 → 最后函数**，每改一类立即编译。

- 每次修改都必须实际编译，并贴出 `lastbuild` 中 `Compilation succeeded/failed` 的原文。
- 无法实际编译时，明确说明“尚未验证”，不得声称编译通过。
- 完成后报告：改了什么、改了哪些文件、验证结果、未解决问题。

## 2.4 页面伪代码格式（强制四列）

| Command | Caption（页面显示的中文） | 调用对象 | 封装 |
|---|---|---|---|

# 5. VTT / vTESTstudio 专项规则

## 5.1 页面步骤输出要求

- 先给**最终 Sequence / Test Tree 结构表**，按页面实际顺序列出 Preparation、每个 Test Case 实例、实例间 Wait 和 Sequence Completion；之后再给**每个 Test Case 的完整内部步骤表**。
- 两类表均使用四列：`Command`、`Caption（页面显示的中文）`、`调用对象`、`封装`。每个可见页面步骤单独一行，明确实际调用对象与封装形态。
- 重复运行同一 Test Case 时，在最终序列中逐个列实例及参数；该定义的完整内部步骤表列一次即可。多个不同 Case 必须分别列出各自完整步骤，不用“同上”代替。
- Preparation / Completion 的位置与项目固定模板保持一致；如模板不含某级 Completion，不得自行增设，先指出实际模板差异。
- 不输出未经确认的代码实现，不引入清单之外的变量、函数或测试组件。

## 5.2 TestCase 复用规则

1. 优先复用项目已有封装 TestCase，但先确认目标编辑器/版本是否支持当前调用层级（例如 Test Case 是否允许嵌套）。
2. 若平台禁止嵌套或其他限制使复用不可行，不能伪装为已复用，也不能违反平台限制；简要指出冲突及影响，并在用户确认后采用等价的页面可见原生步骤，或等待用户指定处理方式。
3. 只有在用户确认替代后，才可按已确认判据实现等价步骤；不得借机增加或改变流程、判据。
4. 每个测试步骤必须标注实际调用的 TestCase、函数或原生节点。
5. 没有合适封装时，明确指出缺失，不得假装已有。

## 5.3 Preparation / Completion 固定格式

1. 项目级 Preparation / Completion 严格使用用户提供的固定格式，不得增删字段、修改字段顺序或字段名称。
2. Test Case 自身的 Completion 属于独立页面节点，不得擅自把项目级 Completion 模板复制或改写成 Case Completion。
3. 如安全收尾确实要求新增 Case Completion，先说明它与固定模板的区别及必要性，取得用户确认后再实施；不得因此改变项目级模板。
4. 未获得原始模板时，必须向用户索取，不得猜测。

## 5.4 节点选择原则

1. **流程必须写在 Test Table 的 Function 和 Test Case 里，步骤要在页面上看得见。**
   禁止用一个 CAPL 函数包住整套流程。
2. 能用原生节点就用原生节点：`awaitvaluematch`、`statecheck`、`wait`、`set`、
   `linstopscheduler`、`linstartscheduler`、`while`。
3. 不手写轮询循环；需要等待条件时优先用 `awaitvaluematch`。
4. CAPL Inline 只做少量补充，且只能使用 `@sysvar::`、`syspar::` 与 CAPL 内建函数。
5. 参数填错类校验一律不加；只保留写坏变量或安全互锁相关的约束。
6. 判据参数（容差、限值）不得放进 Mode 分列，否则等于允许调试时放宽判据。

## 5.5 输出前强制自查

- 所有变量、函数和系统变量均有资源来源；新增项明确标为拟新增并经用户确认。
- 所有已有 TestCase/Function 的复用方式符合当前版本平台限制。
- 新增 TestCase 已明确标注为新增，且用户已确认其页面定义。
- 页面表同时包含最终 Sequence/Test Tree 和每个 TestCase 的完整内部步骤。
- 没有未经确认地复制、拆分或改变已有逻辑。
- Preparation / Completion 严格符合实际固定模板；若安全或平台限制导致无法照用，先指出冲突并取得用户确认。
- 所有步骤符合实际测试流程，且没有虚构资源或接口。

**有一项不符合，先修正；资源不足或存在影响实施的矛盾时，仅提出必要的澄清问题。**

## 6.2 CAPL 与报告

| 事实 | 影响 |
|---|---|
| CAPL Inline 是独立编译单元 | 不能调用 `.can` 的函数或变量（报 `1156 unknown function` / `1053 Unknown symbol`）。要调用就写 `<caplfunction>` |
| `write()` 不产生报告步骤 | 只有 `testStepPass` / `testStepFail` 会成为报告里的步骤 |
| `testWaitForTimeout` 每次调用都记一条报告 | 轮询间隔用 200 ms，不要用 10 ms |
| CAPL 无 `Sleep` / `Delay` 类函数 | 已查 vTESTstudio CHM 的 418 个 Test 函数，无免记录的纯延时 |

## 6.3 Test Table 语法

| 事实 | 说明 |
|---|---|
| `<export>` 只能是布尔 | 写 `none` 会 schema 校验失败，整份 VTT 打不开 |
| `<caplfunction>` / `<ttfunction>` 不可混用 | 前者调 `.can` 的 `export testfunction`，后者调 Test Table 内部 Function |
| `<caplfunction>` 可用于 Test Case 内 | 已实测编译通过 |
| `statecheck` 支持 `range/based` | 上下界一次表达，不必写两个判断；也支持一个 `expected` 内多个 `compare` |
| `awaitvaluematch` 超时可引参数或变量 | 但不能在 XML 里做加法，需先用 Inline 算好再引用 |

## 6.4 dbobject 路径格式（写错即编译失败）

```
系统变量：SysVar_BEGIN_OF_OBJECT|1|变量名|命名空间|-1|0|END_OF_OBJECT_SysVar|
参数：    ChParScalar_BEGIN_OF_OBJECT|1|IBS::参数名|END_OF_OBJECT_ChParScalar|
网络：    Network_BEGIN_OF_OBJECT|1|LIN|5|1|END_OF_OBJECT_Network|
```

## 6.5 继电器语义（按接线图确认）

| 通道 | 触点类型 | 0 | 1 |
|---|---|---|---|
| `BatteryConnectEquipment` | 常开 | 未连接 | 接入电池 |
| `CAB1500_PowerCtrl` | 常闭 | **接通** | **断开** |
| `IBS_PowerCtrl` | 常闭 | **接通** | **断开** |

- 休眠电流测量要求 CAB1500 接通，即准备态元组应为 `(0,0,0)`。
- 带电切换禁止：`RELAY_Set` 要求输出已关且 DVM 低于 `TB_MaxSwitchVoltage_V`。
- 测试中确需切换继电器时，用 `RELAY_SafeSwitch_Check(state)`：内部先关输出、等电压落下、再切、再恢复。

## 6.6 Mode 参数分列

- 用 `ScalarMultiRecord` + `SelectorType	[Mode]		Normal	Test`。
- 多列记录的 `Type` **必须写 `Auto`**，不能写 `Integer` / `Float`。
- 同一 Group 内可以同时存在 `ScalarSingleRecord` 与 `ScalarMultiRecord` 块。
- `Mode` 的 `PossibleValues` 为空不影响列绑定。
- `Mode` 绑定关系存放在 `.vtsoproj` 的测试单元 `EmbeddedTUVariantProperties` 里，
  同时 `.vvarprop` 中该属性的 `Modifiable` 需为 `true`。
- 参数分组按测试用例管理：核查各用例是否有独立参数组，只给缺组的用例补组；已有组保持不动，不为统一命名或结构重整。
- 用例专属参数放在该用例自己的组中，即使别的用例组已有同用途参数，也不跨用例组复用；新建不同名称的参数。通用设备/阶段参数仍按其原有职责使用。本规则是上文“优先复用现有资源”对用例专属参数的例外。
- 测试时长**超过 3 分钟**（严格大于 180000 ms）的用例专属时间参数使用 `Mode` 的 `Normal` / `Test` 分列；`Normal` 保持原测试时长，`Test` 参考工程现有 Test 列的量级缩短测试时间。等于或小于 3 分钟的时长不因本规则强制改造。
- `Mode` 只用于缩短执行时间，不用于改变容差、限值等测试判据；新增参数应接入对应测试步骤，不能只在参数文件中建组而让步骤继续使用硬编码时长。

## 6.7 SOC 唤醒请求测试：用户已确认的流程约束

以下结论适用于本工程当前 IBS/CANoe 12/vTESTstudio 4.0 项目及本次 SOC 唤醒请求测试；后续同条件任务直接沿用，不重复询问。需求或硬件条件变化时，只指出具体变化及影响。

- 目标是五轮独立测试真实电池满充后由 N8361 11.0 V 条件放电，观察 SOC 低阈值唤醒请求；不是验证充电电流/放电电流唤醒功能。
- 每轮重新完成满充流程：N8361 14.0 V，充/放电限流均 10 A；从首个新鲜 DVM 采样超过 13.5 V 起保持 25 min；之后要求新鲜 `Calc_Data_1::SOC=100` 且 `SOC_STATE=2`。
- 唤醒配置为 `SOCWU_Ena=1`、`SOCWU_Treshold=80`，`ChargeCurrWU_Ena=0`、`DisChargeCurrWU_Ena=0`。
- 休眠判据使用 CAB1500 新采样，电流处于 0..18 mA 有效范围，观察相邻新样本 `<=4 mA` 与 `>=14 mA` 的跳变；LIN `Frames` 不增长。休眠确认窗口 90 s，确认后再等 5 s。
- 停止 LIN 后的 200 s 负向窗口只接受 `testWaitForLinWakeupFrame` 返回 0；正向等待最长 2.1 h，只接受返回 1。返回 -1/-2 或其他结果均为失败。2.1 h 从 N8361 11.0 V 输出开启后计时；电池端实测电压须先高于 11.0 V 才满足放电方向条件。
- 物理 LIN 唤醒帧只证明总线上出现唤醒帧，不证明其来源或原因必为 IBS SOC 请求；`_Statistics::LIN1::Wakeups` 只作诊断，不能单独作为请求/误唤醒判据。需要在恢复通讯后的新鲜帧核对 SOC 唤醒状态及其他电流唤醒状态。
- 每轮失败不得继续后续轮次；单轮异常收尾先关闭 N8361 输出，只有输出命令读回为关闭才断开电池，再停止 LIN、等待 DVM 回零并检查命令状态。命令读回不是物理触点状态证明。
- vTESTstudio 4.0 不支持 Test Case 嵌套。确需使用已有 Case 判据但无法嵌套时，只有在用户已确认后，才可用页面可见的等价原生步骤替代；不可声称直接复用了该 Case。
- 上述流程决策不代表台架验证已通过。未经实际台架执行，不得声称电池过程、休眠电流或唤醒来源已验证。
