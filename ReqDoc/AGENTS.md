- # AGENTS.md

  # 1. 项目技术规范

  - 主要开发语言：CAPL、C、C++、Python、Java。
  - 测试平台：CANoe、vTESTstudio、TSMaster。
  - 优先遵循项目现有代码风格、架构及命名规范。
  - 优先使用当前实际安装的软件版本、驱动和 SDK。
  - 以真实运行环境为依据，不以模型自身知识替代实际接口定义。

  # 2. API 真实性约束（最高优先级）

  ## 2.1 禁止虚构 API

  1. 严禁编造函数、类、变量、结构体、枚举及系统变量。
  2. 严禁将其他软件、其他版本或其他编程语言的 API 直接套用到当前项目。
  3. 严禁为了实现需求而擅自设计驱动不存在的接口。
  4. 不允许将未经验证的 API 当作真实接口使用。
  5. 不允许为了让代码看起来完整而自行补充不存在的接口。

  ## 2.2 API 验证优先级

  按照以下优先级确认接口：

  1. 当前项目已有的实际调用方式。
  2. 当前安装版本的 SDK、头文件、接口定义。
  3. 驱动自带的官方示例及 Demo。
  4. 当前版本的官方 API 文档。
  5. 其他版本的资料，仅供参考，不得直接认定兼容。
  6. GPT 自身知识和推测，不得作为接口存在的依据。

  涉及 API 时，优先核实：

  - 函数名称
  - 参数类型及顺序
  - 返回值
  - 结构体定义
  - 调用约定
  - 版本兼容性

  ## 2.3 不确定时的处理

  - 找不到接口定义时，优先搜索项目文件、SDK 和驱动示例。
  - 仍然无法确认时，明确说明缺少什么资料。
  - 不允许通过猜测接口、创造替代接口解决问题。
  - 区分已验证、未验证和推测的内容。

  # 3. 代码修改规则

  1. 优先修改现有代码，不随意重构。
  2. 不修改与当前任务无关的文件。
  3. 不擅自修改变量名称、函数名称、接口和参数名称。
  4. 优先复用项目现有函数、变量和驱动原生接口。
  5. 不擅自增加中间层、包装函数或抽象架构。
  6. 不为了代码结构漂亮而增加不必要的辅助函数。
  7. 不改变现有功能及接口行为，除非需求明确要求。
  8. 优先采用简单、直接、可维护的实现方式。
  9. 尽量一次性完成相关修改，避免反复小范围修改。

  # 4. VTT / vTESTstudio 专项规则

  ## 4.1 需求确认方式

  1. 当用户尚未明确测试流程或实现思路时，不要急于编写代码。
  2. 先分析现有项目资源，直接输出 VTT 页面测试步骤（Markdown）。
  3. 让用户通过页面步骤判断测试流程是否符合预期。
  4. 用户确认页面步骤后，再进行具体实现。
  5. 不要反复要求用户描述已经可以从项目中查明的内容。
  6. 不要擅自改变用户的测试思路；发现明显逻辑问题时，指出问题并给出简洁建议。

  ## 4.2 编写 VTT 页面步骤前的强制要求

  先列出可用资源清单：

  - 已有变量及参数。
  - 已有 CAPL 函数及公共函数。
  - 已有封装 TestCase。
  - 已有 Test Sequence。
  - 已有固定模板。
  - 已有公共测试组件。

  资源清单必须来源于实际项目，不得凭空补充。

  **清单外资源一律禁止使用。**

  如果缺少必要资源，停止设计并向用户询问，不得自行创建替代资源。

  ## 4.3 TestCase 复用规则

  1. 必须优先复用项目已有封装 TestCase。
  2. 禁止重复实现已有 TestCase 内部逻辑。
  3. 禁止将已有封装逻辑拆开重新实现。
  4. 每个测试步骤必须标注实际调用的 TestCase 或函数。
  5. 如果没有合适的封装 TestCase，明确指出缺失，不得假装已有。

  ## 4.4 Preparation / Completion 固定格式

  1. 严格使用用户提供的 Preparation 固定格式。
  2. 严格使用用户提供的 Completion 固定格式。
  3. 不得增删字段。
  4. 不得修改字段顺序。
  5. 不得修改字段名称。
  6. 不得自行设计新的格式。
  7. 如果没有获得原始模板，必须向用户索取，不得猜测。

  ## 4.5 VTT 页面步骤输出要求

  - 使用 Markdown。
  - 直接展示 Test Tree / Test Table 页面步骤。
  - 按实际执行顺序排列。
  - 每个步骤标注调用的已有 TestCase 或函数。
  - 明确 Preparation、测试执行、Completion 的位置。
  - 不输出未经确认的代码实现。
  - 不引入清单之外的变量、函数或测试组件。

  ## 4.6 输出前强制自查

  每次输出 VTT 页面步骤前检查：

  - 所有变量均在资源清单内。
  - 所有函数均在资源清单内。
  - 所有 TestCase 均为已有资源。
  - 已复用已有封装 TestCase。
  - 没有重复实现已有逻辑。
  - Preparation 格式完全一致。
  - Completion 格式完全一致。
  - 所有步骤符合实际测试流程。
  - 没有虚构任何资源或接口。

  **有一项不符合，必须重新检查和修改；资源不足则停止并询问用户。**

  # 5. 执行规则

  ## 5.1 任务处理

  1. 先定位目标文件，不扫描整个项目。
  2. 阅读目标代码及必要的关联代码。
  3. 小修改直接执行，不需要制定复杂计划。
  4. 多文件修改才进行必要的任务规划。
  5. 简单任务禁止无意义地调用子智能体。
  6. 不重复读取已经掌握且未发生变化的文件。
  7. 不进行与当前需求无关的代码分析和重构。

  ## 5.2 修改验证

  1. 修改前确认相关接口及参数定义。
  2. 修改后进行必要的编译或静态检查。
  3. 优先使用当前实际安装环境进行验证。
  4. 编译失败时，根据真实错误定位问题。
  5. 不允许通过创造新 API 或修改无关代码绕过错误。
  6. 无法实际编译时，必须明确说明尚未验证，不得声称编译通过。

  # 6. 工作方式约束

  1. 优先解决用户当前提出的问题，不擅自扩大需求范围。
  2. 不要过度设计流程或架构。
  3. 不要为了追求理论上的完整性增加不必要的步骤。
  4. 不要反复讨论已经明确的需求。
  5. 不确定时，先利用现有项目资料进行查证。
  6. 只有遇到影响实现的关键问题时，才向用户提问。
  7. 不要把推测当作事实，也不要为了迎合用户而隐瞒技术限制。
  8. 如果实际驱动不支持某项功能，直接说明，不要虚构实现方案。

  # 7. 回复规范

  1. 简洁回复，只列关键点、命令和必要结果。
  2. 不需要客套话和冗长解释。
  3. 用户没有要求时，不主动展开技术原理。
  4. 细节等用户主动询问后再补充。
  5. 需要用户判断时，直接提供可判断的实际内容，不要只描述思路。

  # 8. 输出要求

  每次完成任务后：

  - 简洁说明修改内容。
  - 列出实际修改的文件。
  - 说明验证结果。
  - 指出尚未解决的问题及未验证内容。
  - 不输出无关分析和冗长的执行过程。

  # 9. 核心原则

  **真实接口优先于模型知识，实际环境优先于理论推测。**

  **先查证，再实现；不确定就说明，不允许脑补。**

  **先给 VTT 页面步骤，再由用户确认，最后执行实现。**

  **优先复用现有资源，不重复造轮子。**

  **优先解决实际问题，避免过度设计，减少无效操作。**
